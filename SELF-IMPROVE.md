# SELF-IMPROVE

Gotchas from concrete runs in this repo. When you hit one again, increase its count and keep the list sorted by count, largest first.

- 2x **Two pytest runs must not overlap: they share `data/memelord.db`.** There is no per-run test database (plain `django.test.TestCase` on the dev DB), so a second `pytest` started while the first is running risks `database is locked` and spurious failures; the only safe option is to serialise runs (wait for `exit=` in a background run's log before starting the next). The same holds for any `manage.py` command that writes rows (e.g. a real `index_search --limit 5` smoke run) while a background suite is on. Cost: one blocked turn while a 2.5-minute full run finished before a 30-second module could start; on 2026-10-03 again a 4-minute wait before the real-model smoke run. Candidate fix: pytest-django with a throwaway DB, or a `DATA_DIR` copy per run (the mutation run already uses a copy).
- 2x **mutmut 3 flags import-heavy mutants as timeouts and then crawls.** Each mutant runs in a forked child that pays the lazy `transformers`/torchvision import (~10 s wall) the covering test never shows in its own timing, so the default wall limit (`cpu_limit/2` = 15 s for fast tests) kills cleanly dead mutants as `timeout`, and every timeout restarts the fork server (~1 min per mutant). Diagnose by running the covering test by hand with `MUTANT_UNDER_TEST=<id>` from inside `mutants/`; fix with `timeout_constant` in `[tool.mutmut]` (set to 3.0 here). Cost: one aborted run plus the investigation. 2026-10-03 again: a run over the full `only_mutate` scope (1162 mutants) with both test dirs selected managed 5 mutants in 25 minutes, all timeouts, and had to be killed. Narrow `only_mutate` *and* `pytest_add_cli_args_test_selection` to the changed modules and their test modules for every run (restore both afterwards); the scoped run is the only one that finishes.
- 1x **A SQLite partial index is only used when the query spells its condition the same way.** `models.Index(condition=Q(embedding__isnull=False))` becomes `WHERE embedding IS NOT NULL`; a count written as `.exclude(embedding=None)` renders `NOT (embedding IS NULL)` and SQLite falls back to the review-queue index and reads every wide row (88 ms vs 2 ms on the 25k copy). Write the filter as `.filter(embedding__isnull=False)` and pin the plan with `.explain()` (contract R5 does). Cost: one plan-reading detour (2026-10-03).
- 1x **A `DATA_DIR` copy must copy `images/`, a symlink 404s every picture.** `memelord.media._resolve_media_file` resolves the path and requires it to stay under `MEDIA_ROOT`, so a measurement copy with `images -> ../data/images` serves 404 for every image while the DB rows look fine; hard links fail too when the copy sits on tmpfs (`Invalid cross-device link`). Copy the directory (240 MB, a few seconds). Cost: two measurement runs that reported 3 KB error pages as "images" (2026-10-03).
- 1x **A synthetic DB copy without the vector blobs understates query cost by about 2×.** The image rows carry two 3 KB vectors, so a full-table scan over 25k rows reads ~150 MB; rows bulk-created without `embedding`/`search_embedding` made the same queries look half as slow (POST 136 ms vs 266 ms with blobs; the live server showed 4.5 s). Give synthetic rows blobs (`os.urandom(3072)`) before measuring, or measure on a real copy. Cost: one re-baseline (2026-10-03).
- 1x **The venv's Playwright needs its own browser build.** `~/.cache/ms-playwright` held chromium builds from other installs, but the venv's `playwright` wanted `chromium_headless_shell-1243`; the first launch failed with "Executable doesn't exist". Run `uv run playwright install chromium-headless-shell` once before a measurement. Cost: one failed run (2026-10-03).
- 1x **Plain pytest-function tests write permanently to the dev DB.** `tests/memelord/test_media.py` and `test_auth.py` create a user per test through a fixture outside any `TestCase` transaction, so the dev DB has accumulated 400+ `media_*`/`auth_*` users (seen 2026-10-03). Harmless so far, but any fixture row that is not inside `django.test.TestCase` stays forever. Use `TestCase` (or wrap in `transaction.atomic()` + rollback) for anything that inserts. Cost: none yet, flagged for the shared-DB cleanup.
- 1x **django-q's `scheduler()` and ORM broker cannot run inside a `TestCase`: they close the shared SQLite connection.** A test that called `django_q.scheduler.scheduler(get_broker())` to observe catch-up behaviour passed its own assertions and then took every later test in the class down with `Cannot operate on a closed database` (the broker calls `close_old_connections`, which ends the test transaction). Pin django-q behaviour on configuration (`Conf.CATCH_UP`, `Q_CLUSTER[...]`) or on the Schedule/OrmQ rows your own code writes; never drive the cluster, the scheduler or `async_task` with the real broker in a DB test. Cost: one red run of ten tests and a rewrite of the V4 test (2026-10-03).
- 1x **Tests run against the real dev DB, so a new migration must be applied before the tests can pass.** The suite uses plain `django.test.TestCase` without pytest-django, so there is no test database: every test opens `data/memelord.db`, deletes rows inside a transaction and rolls back. A new model field therefore fails every DB test with `no such column` until `DJANGO_DEBUG=true uv run python manage.py migrate` has run locally. Cost one full test cycle. Candidate fix: document it in CLAUDE.md under Tests (done) or move to pytest-django with a throwaway DB.
- 1x **Resuming a mutmut run after editing sources or tests corrupts the test mapping.** A second `mutmut run` on an existing `mutants/` tree (source docstrings changed, 3 tests added) re-collected stats and then reported 473 of 577 mutants as `no tests`, dropping the cached kills as well, so the tally was meaningless. Always `rm -rf mutants` before a run whose sources or tests changed; the fresh full run is cheaper than the triage of a broken one. Cost: one wasted run.
- 1x **`uv run pytest` silently ran a system pytest.** When uv re-creates `.venv` (it does so on an interpreter change) without the dev tools, `uv run pytest` falls through to `~/.local/bin/pytest`, which cannot see Django and fails collection with `ModuleNotFoundError: No module named 'django'`. Fixed by moving dev deps to `[dependency-groups]` so they sync by default. If it recurs, check `ls .venv/bin/pytest` before debugging anything else.
- 1x **Parallel `uv run` calls race on venv re-creation.** Two `uv run` invocations started together while uv was rebuilding `.venv`; one saw a half-populated site-packages and failed. After a Python or lockfile change, run the first `uv sync`/`uv run` alone and only then fan out.
- 1x **Mocking `transformers.AutoImageProcessor` at module level does not take effect.** transformers resolves that name lazily, so `mock.patch("transformers.AutoImageProcessor")` leaves `from transformers import AutoImageProcessor` inside the function returning the real class (while `AutoModel` happens to work). Patch the project's own loader seam (`core.brain._load_from_hub`) instead. Cost one red run plus a debugging detour.
- 1x **The DINOv3 weights are gated, so the real-model check needs a granted Hugging Face account.** Meta approves access requests manually (took about an hour on 2026-10-02). Until then the opt-in test `uv run pytest --run-integration tests/core/test_brain_integration.py` stops at the licence error, which is the expected failure, not a bug. On a fresh machine set `HF_TOKEN` in `.env` first; the download is ~330 MB and lands in the HF cache (the compose `hf-cache` volume in Docker).
- 1x **A page-wide context processor can undo what a coarse mock pretends.** `active_jobs` runs on every page and reconciles the session's task id with the broker: a `fetch` mock that answers "completed" for every id makes the processor clear the session, so a test asserting "the job is still shown" fails for the right reason. Mock per id (`side_effect = lambda task_id: ...`) whenever a view and a processor both look at the same task. Cost: four red tests and a detour through the processor.
- 1x **The dead-CSS guard fires on the next run after any markup removal.** `test_every_css_class_is_used_somewhere` compares every class in `app.css` with templates and JS, so deleting a template or a JS lightbox leaves orphaned rules that fail the suite one run later. Grep `static/app.css` for the classes of the markup you remove before running tests. Cost: two red runs.
- 1x **Hypothesis' Django `TestCase` calls the first `setUp` before `_pre_setup`, so `self.client` does not exist there.** Log in and seed inside the test body (or in `setup_example`), not in `setUp`. Plain `django.test.TestCase` is unaffected. Cost: one red run.
- 1x **`gallery.html` assembles its filter URLs by hand in four places.** Every score, sort and tag link spells out `?min_score=…&sort=…&tag=…`, so a new sticky parameter (the search text, the scope, the similar anchor on 2026-10-03) means editing each link and remembering `urlencode` for the hostile one. The view now hands the template a prebuilt `sticky` string, `scope_urls` and `clear_url`, which halves the problem but leaves the old links as they were. Candidate fix: one `{% gallery_url min_score=… %}`-style template tag (or a view helper that builds every control URL) so a new parameter is one line. Cost: one careful template rewrite and a dedicated escaping test.
- 1x **`pkill -f "mutmut run"` kills the shell that issues it.** The pattern also matches the `bash -c '... pkill -f "mutmut run" ...'` command line of the tool call itself, so the shell died with exit 144 before reporting, and the next turn had to find out blind whether mutmut was gone. Use a pattern that cannot match its own command line (`pkill -f "[m]utmut run"`) or kill the PID captured when the run was started. Cost: one lost turn.
- 1x **A background chain is spread over nine files.** Adding the taste re-encode chain next to the search index chain meant mirroring the stale/count/queued/enqueue/report helpers, a `tasks.py` entry point with the stop rule, two views, two URLs, a context-processor block, two pending/result templates, the `_nav_job.html` conditions and a `config.html` block, plus a mirror test module, with only names and wording differing. Two copies are still cheaper than the indirection, but a third chain is the moment for one `ratings/chain.py` object (task name, stale queryset, slice size, wording) and one generic pending/result template. Cost: a long, careful copy-and-rename pass and the matching test mirror.
